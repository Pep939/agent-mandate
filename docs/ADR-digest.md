# ADR Digest — Plain English (2026-09-04)

What the 14 ADRs actually decide, one screen each. The formal records live in
`docs/decisions/`; this digest exists so the maintainer can verify the "why"
without reading all of them. Statuses as of 2026-09-04: **0001–0013 accepted**
— 0001–0009 through the phase-gate breakdowns, 0010 with its committed
Phase 4 step 2 (plus the Phase 5 conformance fix), 0011 with the step 3
console, 0012 with Phase 6 (two-machine transport), and 0013 with Phase 7
(the self-run shadow pilot) built this session. **0014 proposed** (schema 0.2:
revocation becomes a chain event; append-only scope on all governed tables;
gateway-key custody), pending maintainer approval.

| # | Decision in one line | Why | What it locks in | The part worth poking |
|---|---|---|---|---|
| 0001 | One program, not a fleet of microservices | Failure modes before the core claim is proven buy nothing | Strict inside-out boundaries; the policy core never touches the database | Two-machine Phase 6 = two copies of this monolith, one per machine — not a rewrite |
| 0002 | No blockchain in v0.1; addendum pins the one trigger to revisit it | The trust properties come from signatures + hash chain, not from a chain | On-chain features only as later adapters; private contents never on-chain | The trigger: a third party must verify a history they hold no copy of (e.g. public dispute, auditor) |
| 0003 | Python 3.13, not the brief's 3.12 | Your standing rule is 3.13-only and outranks the draft brief | Interpreter floor for the whole repo | None — plumbing |
| 0004 | 11 spec ambiguities set to explicit defaults | The specs had `AMBIGUITY` markers that needed owners | Any future change to a row is a **new ADR**, never a silent code edit | A2: over-cap spend goes to a **human**, not auto-deny — the most product-facing row; the approval console exists to serve it |
| 0005 | One signing algorithm (Ed25519), one byte format, keys never in the repo | A signature is only as strong as the consistency of the bytes it signs | One canonical serializer for the entire product (invariant 13); dev keys generated at runtime | Production key custody (HSM, rotation) is deliberately deferred to Phase 4+ |
| 0006 | Delegation can only **narrow**, never widen | A sub-agent's power is a subset of its principal's, field by field | Revoking a parent voids every descendant — rechecked on **every** action, not just at creation | No depth limit in v0.1: unlimited delegation chains, as long as each link narrows |
| 0007 | Replayed and duplicate requests are rejected or answered from memory | Crashes and retries must never double-process (invariant 14) | A retried request gets back its **original** decision; a key reused for a *different* proposal is treated as hostile, not a typo | The check order (idempotency first) is subtle and load-bearing |
| 0008 | History is append-only, enforced three ways | Trust has to survive a bad operator, not just a bad agent | DB role can't edit events; a DB trigger refuses even UPDATE/DELETE; the hash chain makes any change *provable* | Honest ceiling: a fully compromised operator can still truncate their own DB — we **detect**, we don't prevent |
| 0009 | Every decision is written; every write is one atomic transaction | This is what makes "every decision reconstructable" literally true | Allow, deny and needs-approval all land in the ledger; a stale or racing write writes nothing (recheck against stored state first) | Denials consume ledger space on purpose — the evidence trail must show refusals too |
| 0010 | **Accepted.** Approvals: a human "yes" is itself a signed, one-time, single-proposal override | The override must carry the same trust properties as the mandate it extends | Bound to the exact action + amount; re-checked at decision time (revoked/expired parent or moved-on deal → auto-deny); grants and denies both logged | Approvals have no own expiry — they die only when their parent mandate dies |
| 0011 | **Accepted.** Console security: loopback-only, single operator, CSRF token per form, secrets at startup only, agent text rendered as escaped text | The first real attack surface is the web console; state the local threat model instead of hiding it | 127.0.0.1 binding, session cookie, constant-time password compare, banned-secret scan, untrusted content never becomes HTML | No TLS, no multi-user in v0.1 — a documented limitation, fine locally, must be revisited at Phase 6 (two machines) |
| 0012 | **Accepted.** Two-machine transport: gateways authenticate each other with pre-shared Ed25519 identity keys; every wire message is a signed, versioned JSON envelope; retries answer from the idempotency store, never reprocess | The wire is the first genuinely hostile surface; the signature is the auth (no login), and the receiver's policy engine — not the sender — is the only path to a state change | Envelope schema (9 fields), three kinds (proposal / counterparty_event / receipt), verify-first pipeline, sync push only, identity key ≠ chain key, peer id = the mandate's `counterparty_id` | No TLS, no payload encryption, no PKI, no rate limiting — an on-path host can read message structure but cannot forge or modify |
| 0013 | **Accepted.** Phase 7 shadow pilot: drive a synthetic field-service day through the real console + policy + ledger over HTTP; a human grants/denies every approval; nothing auto-commits; capture is a ledger record, not a charge | Phase 7 is a validation exercise, not a product feature — the question is whether the whole thing holds across a realistic multi-deal day with a person in the loop | Console-driven (not the wire); outcomes read from the ledger, not HTML; a human grant is the only thing that moves an approval-gated action; a reproducible digest makes two runs byte-comparable | The CRM/Jobber adapter is deliberately deferred (gated on account access and demonstrated demand); no payment provider until Phase 8 |
| 0014 | **Accepted 2026-09-04** (amended same day, implementation pass). Schema 0.2: revocation becomes a seventh chain event (`REVOCATION`); the append-only trigger covers all eight governed tables (plus TRUNCATE guards); the least-privilege role becomes real DDL; v0.1 key custody = persisted gateway key | Revocation is an authority decision, so it must be reconstructable from the chain alone (invariant 5) — today deleting a side-table row silently un-revokes, and the hash chain never notices | `REVOCATION` event type (payload = the signed `Revocation` record, lands on the linked deal's chain); triggers on 8 tables, `deals` + `approvals` excluded (current-state projections — amendment: the draft's 9th table, `approvals`, is rewritten by `commit_approval` by design); `mandate_app` role DDL (UPDATE on the two projections only); principal key deferred to the standards-adapter phase | Deals that experience a revocation gain an event (no existing pinned digest changes — verified); revocation over the wire stays deferred (a fourth envelope kind is its own decision) |

| 0015 | **Accepted.** The evidence bundle's summary is signed by the gateway's chain key | Hashes alone let a re-exporter with DB access truncate the tail and recompute a "clean" summary | `summary_signature` over a canonical summary payload; `build_bundle` needs the private key; schema 0.1 → 0.2 | An attacker holding the chain key can sign a truncation — but they already hold the root of trust for every event |
| 0016 | **Accepted 2026-09-21.** A content screen reads free text, and may only make a decision *more* careful | Nothing in the system read meaning, so `disclosure_fields` was an agent self-declaration and threat-model gap G1 stayed open. A typed classifier returns numbers, which a pure function can read and a chain can sign | Claims enter `PolicyInput` like `signature_valid`; step 9b denies a near-certain undeclared disclosure, 12b holds on a probable one / hostile text / an unavailable screen; integer basis points; pinned screener + question digest in a MESSAGE event; vendor behind a swappable interface, off by default | The narrowing rule is the whole safety argument, and it is property-tested: a fooled screen can only cost availability. What it does **not** claim is that any given screener is accurate |

## How to use this

- Something in a row looks wrong? Say which and what you'd change — it
  becomes an amendment or a superseding ADR, and the code follows.
- 0001–0014 are accepted (0014 approved 2026-09-04, amended same day). Flag any you
  want re-opened and I'll treat it as a new ADR and log it in
  an amendment or a superseding ADR.
